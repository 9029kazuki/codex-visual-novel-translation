# 审校、质量门禁与发布

## 自动 QA

任务级和全局级分别运行验证，至少检查：

- JSONL 可解析，ID 唯一、顺序正确且覆盖计划范围。
- 验证器根据 ID 从冻结原文重建 `source_hash`；草稿若显式携带 `source_hash`，则必须一致。
- `protected_tokens` 的内容、数量、顺序和嵌套不变。
- 换行、转义、变量、标签、语音及说话人关联未破坏。
- 锁定/禁止术语、人名、地名、称谓和敬称策略。
- 同一原文或复用文本的译法一致性。
- 空译文、原文照抄、残留日文、异常长度、乱码和不支持字形。
- 译文编码和引擎限制。
- `chunk-plan.json` 与 `coverage-plan.json` 证明每个计划 ID 恰好作为 primary 处理一次，overlap 没有重复输出。

自动检查发现 error 时失败关闭，不继续回填。warning 必须由主智能体裁决并记录。纯标点原文不变、受保护标记内假名和较长术语已命中时的较短子串，应由验证器直接排除，不产生需人工重复裁决的噪声 warning。

## 语义审校

审校者逐场景检查：

- 否定、双重否定、条件、时间先后和因果。
- 主语、宾语、动作主体、授受、被动和使役。
- 指代、性别、数量、亲疏距离和称谓变化。
- 人物在当前路线节点知道什么、不知道什么。
- 人设、语气、情绪递进、笑点、双关和悬念。
- 旁白视角、时态与文本节奏。
- 选项与选择后反馈是否语义对应。
- 是否出现无依据的网络梗、解释性增译或提前剧透。

低置信度、术语提案、路线交叉点、结局和谜底场景必须由主智能体重点复核。

### 稀疏审校 delta

独立审校必须阅读完整 job，但 review JSONL 默认只输出需修订的条目，不再为每个正确条目重复写 `approve`。每条 delta 格式：

```json
{"id":"common_001.ks:000042","reviewer_translation":"……原来是这样。","reason":"修正否定范围","severity":"major"}
```

同时写入 `reviews/<job_id>.report.json`，至少包含：

```json
{"schema_version":2,"job_id":"job-00001","reviewed_source_digest":"sha256:...","reviewed_draft_digest":"sha256:...","reviewed_entry_count":607,"coverage":"all-entries","delta_count":31,"passed":true}
```

`coverage: all-entries` 声明代表其余条目均默认 approve；只有 report 中的原文/草稿摘要与当前文件一致时才有效。物化批准稿时，对 delta ID 使用 `reviewer_translation`，其余 ID 使用草稿译文。稀疏输出只减少冗余，不减少独立审校的覆盖。

## 跨分批与全局一致性

一个 job 的所有 chunk 完成后，进入审校前先做一次轻量全 job 扫描，至少检查称谓、术语、人名、跨批指代、时间顺序、重复原文与场景收束。全部 job 物化后再做全项目一致性扫描。

## 缓存与调用可观测性

若宿主提供 input/cache/output 计数，按 cohort 和 job 记录到 `qa/cache/`，分别报告总输入、缓存输入、非缓存输入、输出和调用数；不把缓存 Token 当作零成本。每次还应记录 prefix ID/哈希、bundle 大小、chunk 数和历史继承模式。同一 prefix cohort 频繁失去缓存命中时报告为效率异常，但不降低翻译质量门禁。

## 回填 QA

在回填后、封包前检查：

- 目标脚本能够被引擎解析或由现有编译器重新编译。
- 相对路径、大小写、资源引用和语音 ID 未变化。
- 原始换行风格、BOM 和编码符合已验证方案。
- `qa/font-coverage.json` 证明随补丁发布的目标字体或明确的字体回退链覆盖全部实际显示字符，缺失数为 0。
- `qa/font-runtime-report.json` 证明引擎在初始化、恢复已有设置后及各类文本表面上实际选择了预期字体。完整要求见 [font-runtime.md](font-runtime.md)。
- 文本框、姓名框、选择按钮、日志、历史记录和存档标题无明显溢出。

## 实机测试矩阵

至少覆盖：

1. 启动、新游戏、设置、退出。
2. 读档、存档、快进、自动播放、历史记录和回滚（若有）。
3. 公共线代表场景、每条目标路线入口、关键选择肢、结局和返回标题。
4. 立绘/语音/文本同步，等待与换页标签。
5. 最长姓名、最长选项、最长对白和含特殊控制符的场景。
6. 非默认安装路径和无原始 staging 文件环境下的补丁安装。
7. 字体补丁分别在全新配置和已有存档/系统变量环境下测试正文、姓名框、选项、历史记录、设置及存档标题；使用目标语言特有字符探针确认不是日文字体或错误回退字体。

把每项结果、截图或日志路径写入 `qa/playtest-report.md`。未覆盖项必须明确列为已知风险。
同时写入机器可检查的 `qa/playtest-report.json`，只有全部约定测试通过时才设置 `passed: true`。
静态字形覆盖不得替代实机字体选择验证；实机某一正文行正常，也不得替代未测试文本表面的记录。若游戏含多个独立渲染器，应逐一列出 `pass`、`fail` 或 `not_tested`。

## 发布内容

从已验证的 `build` 生成 `release`。包含：

- 补丁文件或安装器。
- 适用游戏版本和原始文件校验和。
- 安装、卸载和故障恢复步骤。
- 汉化范围、未覆盖内容、已知问题和测试矩阵摘要。
- 构建标识、资料库版本和最终 QA 报告。

发布前比较源目录、构建目录和发布目录，只保留预期改动。验证补丁能够在干净游戏副本上应用并启动。
把封包与启动证据写入 `qa/repack-report.json`，把最终干净副本验证写入 `qa/release-report.json`；阶段门禁要求对应报告的 `passed` 为 `true`。全局译文验证固定输出为 `qa/global.json` 且 `errors` 必须为 0。

## 完成判定

只有所有计划任务为 `merged`、全局验证无 error、回填与封包成功、实机矩阵达到约定覆盖范围且发布物在干净副本验证通过时，才将 `run-state.json` 更新为 `released`。
