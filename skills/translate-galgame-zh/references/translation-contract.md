# 日译中翻译契约

## 目标

把日文 Galgame 文本翻译为自然、准确、可直接回填的简体中文。优先级从高到低：

1. 剧情事实、逻辑关系、否定和时态。
2. 说话人、指代对象、视角、主客体和人物知识状态。
3. 人设、情绪、关系距离、称谓和角色口吻。
4. 自然流畅的中文表达与场景节奏。
5. 原文表层词序和形式。

## 不可违反的结构规则

- 逐条输出 JSONL，不输出 Markdown、解释、序号或代码围栏。
- 每个输入 ID 恰好输出一次，保持顺序，不增删、合并或拆分文本单元。
- 原样返回 `id`。精简模型视图不要求每行重复 `source_hash`；验证与合并必须从冻结原文清单核对并补回。若输出中包含 `source_hash`，则必须与原文逐字一致。
- 原样保留所有 `protected_tokens`，包括内容、大小写、数量、顺序和嵌套。
- 保持必要的换行、转义、变量、标签、占位符、颜色/振假名/等待控制和语音关联。
- 不翻译脚本代码、资源名、标签名和变量名。
- 只翻译 `text` 字段；不要改说话人字段或其他元数据。
- 不确定时在结构化 `issues` 中报告，不要猜测后偷偷写入译文。

## 语言规则

- 对白按人物真实说话方式翻译，旁白按作品既定叙述视角和文体翻译。
- 优先传达语气功能，不机械复制日语语尾、主语省略或敬语形式。
- 不凭空补“我、你、他/她”。结合说话人、动作主体、上下文和路线状态判断；无法确认时尽量保持中文可接受的省略或中性表达。
- 严查使役、被动、使役被动、授受、双重否定、省略主语、反问、条件、推量和时间先后。
- 保留原文有意的暧昧、误导、停顿、重复、吞词、口吃和未说完；不要提前解释谜底。
- 不把后续剧情知识写进当前尚不知情人物的台词。
- 遵守锁定术语、人名、地名、称谓与敬称策略。禁止项不得出现。
- 避免没有原文依据的网络梗、流行语、古风腔和夸张粗口。
- 拟声词、昵称、双关和文字游戏以场景功能为先；必要时提交术语/审校问题。
- 中文标点、引号和省略号遵守项目约定，同时满足引擎和文本框限制。

## 完整共享前缀与任务上下文

正式翻译子智能体必须继承与 job 绑定的干净种子历史。该历史中的共享前缀必须完整包含：

- 本翻译契约。
- 世界观和剧情规则。
- 全部角色人设与全部口吻卡。
- 完整称谓、术语和禁用表。
- 完整路线知识门和需要保留的剧情暧昧。
- 批准译例与当前 cohort 的冻结决策。

不得为单个 job 从共享前缀删掉“本场没出场”的角色、术语或知识门；它们共同构成跨子智能体的稳定前缀。任务级可变上下文另行包括：

- 当前任务说明和输出路径。
- 完整当前场景原文。
- 当前路线、时间、地点、前置状态和必要前情。
- 仅用于消歧的后续信息，若提供则不得泄露到译文。

不要只依赖滚动的前几句上下文。完整场景需要分批读取时，严格按 `chunk-plan.json` 的自然子场景顺序处理；每个 ID 只在其 primary chunk 输出，overlap-before/after 只用于理解。每批后校验已完成 ID，最终以 `coverage-plan.json` 确认全覆盖。

## 输出格式

每行格式：

```json
{"id":"common_001.ks:000042","translation":"……原来是这样。","confidence":"high","issues":[],"term_proposals":[]}
```

`confidence` 使用 `high`、`medium`、`low`。只在确有必要时填写：

```json
{"type":"ambiguous-subject","message":"动作主体可能是主人公或美咲，需要前置演出确认"}
```

术语提案格式：

```json
{"source":"御三家","proposal":"三大家族","scope":"global","reason":"本场景明确指三个创始家系","evidence_ids":["..."]}
```

子智能体只能提出术语提案，不能修改 `bible/glossary.tsv`。

## 交付前静默检查

逐条检查：是否漏译或增译；主体对象是否颠倒；否定/使役/被动是否准确；口吻和称谓是否匹配；是否提前剧透；控制符和换行是否原样；是否残留不必要日文；译文是否能装入文本框。完成后只输出 JSONL 文件和简短任务交接，不输出思维过程。
